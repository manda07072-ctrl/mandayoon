# 만다윤 주문·카드결제

옵션을 담은 뒤 카드결제/계좌입금을 선택하고 같은 주문 폼에서 진행합니다. 계좌입금 주문은 기존 서버를 유지합니다. 새 카드 주문은 Sites 주문 서버가 보관하고, Apps Script는 결제 확인 이후 시트 기록을 담당합니다.

## 카드 주문 기록

- 새 주문은 `https://mandayoon-checkout-api.dilec.chatgpt.site/prepare`에서 D1 데이터베이스에 보관합니다. 저장 응답을 받은 뒤 SDK를 호출하며 결제 전에는 Google 요청이 없습니다. `_카드결제대기` 탭은 기존 방식으로 시작한 주문 복구용으로만 유지합니다.
- 주문별 무작위 확인 토큰의 해시를 저장하고, 승인 조회 시 토큰을 검증합니다. 응답에는 배송지·주문자 정보를 노출하지 않습니다. 결제 중 이동에 대비해 브라우저에 확인 토큰을 보관하며 저장 실패 시 결제를 시작하지 않습니다.
- Sites 서버가 서명한 요청은 고정된 서버 주소에서 서명·유효시간·저장된 주문 원문 일치 여부를 확인합니다. 그 후 Apps Script가 실제 PortOne 결제를 조회합니다. 서명 키는 Sites 환경 변수에만 두며 API Secret은 기존 Apps Script에 유지합니다.
- PortOne 조회 API에서 `PAID`, 일치하는 결제 ID·Store ID·KRW 금액, `method.type === 'PaymentMethodCard'`를 확인한 뒤 기존 `주문관리` 탭에 `입금완료`로 기록합니다. 중복 알림도 같은 결제 ID로 한 번만 기록합니다.
- A:P 구조와 C:D 영역을 보존하고 Q열에는 카드결제, R열에는 PortOne 결제 ID를 기록합니다. 주문일시는 한국 시간과 `yyyy-mm-dd hh:mm` 형식입니다.
- 고객에게 승인 결과를 확인한 뒤 시트 기록은 별도로 재시도합니다. 시트 오류가 나도 승인된 주문은 D1에 남습니다. 결제 알림은 재조회 계기일 뿐 승인 증거로 사용하지 않습니다.
- 15분마다 기존 `reconcileCardOrders`가 Sites `/recover`를 깨워 누락 건을 확인합니다. 공개 복구 호출은 전체 서버에서 10분에 한 번, 최대 20건으로 제한됩니다. 새 D1 주문은 불확실 상태에서 자동 삭제하지 않습니다. 기존 대기 탭의 7일 지난 실패·미생성 건 정리와 READY 보존은 유지합니다.
- `setupCheckout`은 기존 미입금 카드 행을 먼저 조회합니다. 승인된 행은 완료로 복구하고, 미완료 행은 임시 영역에 보관한 뒤 주문관리에서 제거합니다. 계좌입금 행은 유지합니다.

## 설정·배포

1. `Code.gs`를 복사하고 스크립트 속성에 `PORTONE_API_SECRET`, `ORDER_SPREADSHEET_ID`, `ORDER_SHEET_NAME=주문관리`를 저장합니다. Secret은 채팅·로그·공개 저장소에 기록하지 않습니다.
2. `setupCheckout`을 한 번 실행합니다. 한국 시간대, 날짜 형식, 임시 탭, 주기적 확인 트리거가 설정됩니다. 실제 승인/취소/환불 요청은 하지 않습니다.
3. 기존 웹 앱 배포를 새 버전으로 업데이트합니다. 소유자 계정으로 실행하고 모든 사용자 접근의 기존 권한을 유지합니다.
4. `?action=ping` 응답의 `ready`와 `version`을 확인합니다. 이는 배포 확인이며 실제 카드결제 성공을 뜻하지 않습니다.
5. 랜딩페이지 `checkoutUrl`은 Sites 서버 URL, `backendUrl`은 이 웹 앱 URL입니다. 새 결제의 `noticeUrls`는 Sites `/webhook`을 사용합니다. 기존 웹 앱 웹훅과 이전 방식으로 시작한 결제의 복구 기능도 유지합니다.

새 흐름은 `Sites prepare 1회 → SDK 호출 → Sites confirm → 실제 승인 조회 → 시트 비동기 기록`입니다. 단계별 로딩·경과 시간과 중복 클릭 방지를 표시하며, 승인 결과가 불확실하면 같은 결제 ID를 다시 조회합니다.

## 속도 비교 (2026-10-21)

동일 컴퓨터에서 실제 배포 서버에 가상 상품·배송지로 5회씩 요청했습니다. 카드 SDK·승인·청구 없이 결제 준비 구간만 측정했습니다.

| 구간 | 기존 Apps Script 저장+확인 | Sites 저장+확인 |
| --- | ---: | ---: |
| 중앙값 | 4,688ms | 117ms |
| 평균 | 4,331ms | 229ms |
| 범위 | 3,327~5,358ms | 102~681ms |

중앙값 기준 97.5% 감소입니다. KCP 결제창 자체의 로딩·실제 카드 승인 시간과 사용자의 기기·통신망에 따른 차이는 포함하지 않습니다. 원시 측정값은 `tests/checkout-timing-before.json`, `tests/checkout-timing-after.json`에 보관합니다. 측정용 주문은 실제 주문과 구분해 정리합니다.

## 검증

`node --test tests/checkout.test.cjs`로 가격·금액, 승인 응답, 중복 처리, 실패·지연 승인, 기존 대기 행 복구와 날짜 설정을 검증합니다.

`node tests/browser-fixture.cjs`를 실행하고 `http://localhost:8765/?scenario=paid#order`에서 모의 화면을 확인합니다. paid, failed, slow, unknown, prepare-error를 지원하며 모든 결제·주문 요청을 가로채 실제로 전송하지 않습니다. `/mobile`은 390px iframe 화면입니다. 모의 검증과 실카드 검증은 구분합니다.
